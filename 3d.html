Что делает CAT

Платёжная система присылает нам колбэк о статусе платежа. Чтобы протестировать обработку, этот колбэк надо воспроизвести — точно, с правильной подписью, по реальной транзакции.

Воспроизвести по id

Берём реальную транзакцию из БД рынка по её идентификатору и дозаполняем ей поля колбэка автоматически.

Собрать запрос скриптом

Тело, подпись, заголовки, URL и query собирает pre-request скрипт — в редакторе, который знает переменные колбэка.

Хранить на всех

Колбэки, шаблоны ПС, переменные рынков и общий код скриптов живут в базе, а не в файле на чьём-то ноутбуке.

История выполнений

Полный запрос и полный ответ по каждой отправке — видно, что именно ушло и что вернулось.

Как было в Postman

И даже не одна коллекция, а куча: у каждого своя, выгруженная в свой момент. Внутри — по запросу на каждую платёжную систему и каждую операцию, и в каждом запросе своя копия pre-request скрипта.

Исправили подпись в одной копии — остальные об этом не узнали. Так появляются sign_v2, sign_final и sign_fixed.

  • Новая платёжная система — скопировать запрос и скрипт, поправить руками. Ошибка копируется вместе с ними
  • Сменился формат подписи — обойти все копии во всех коллекциях. Какую-то обязательно забудут
  • Что ушло вчера и что вернулось — знает только локальная история того, кто отправлял

Почему не Postman

Postman — хороший инструмент. Просто не для этой задачи: нам нужен был не клиент для запросов, а сервис с доступом к данным и общей историей.

Честно: слева — претензия не к Postman, а к тому, как мы его использовали. Пока задача звучала «дёрнуть ручку и посмотреть ответ», коллекции хватало. Не хватило её там, где понадобились общие данные, история и одна версия правды на всех.

Конвейер одной отправки

Восемь шагов от формы до исходящего HTTP-запроса: шесть в prepareCallbackRequest(), потом скрипт и проверка адреса. Порядок важен: секреты изымаются до подстановки, поэтому физически не могут попасть в URL.

Значение берётся с самого сильного слоя: форма → БД рынка → переменные рынка. Как окружение в Postman, только одно на всю команду, и заполняет оно лишь то, что осталось пустым.

Скрипт пользователя в клетке

Pre-request скрипт пишет QA-инженер. Значит, исходить надо из того, что в нём может оказаться что угодно.

  • QuickJS, а не vm и не eval: ни сети, ни модулей в рантайме просто нет
  • Отдельный дочерний процесс с урезанным окружением env: { PATH }
  • Восемь конструкций отклоняются до запуска — astGuard.js
  • 16 МБ памяти, 256 КБ стека
  • Два таймера: interrupt изнутри рантайма и SIGKILL из родителя через timeout + 250 мс

Статический guard знает ровно восемь конструкций: require(, import(, process., child_process, WebAssembly, fetch(, XMLHttpRequest, WebSocket. Единственный пропуск — import … from 'qa-package': он ещё до guard'а переписывается в const { … } = qa. Бесконечный цикл в списке не значится — его останавливает таймер.

QA Package: общий код с историей

Подпись OkPay, сортировка ключей, клиент провайдера — раньше всё это жило копией в каждом скрипте. Теперь это одна библиотека на команду, и у каждого её сохранения есть номер. 

// два равноправных способа
qa.utils.randomString(8)
import { utils } from 'qa-package'
  • Версию считает сервер: клиент выбирает patch, minor или major, номер нельзя переиспользовать
  • История только дописывается: 50 снимков, откат — это старый код новой версией
  • Двое правят сразу — второй получает 409, а не молча затирает первого
  • Типы .d.ts собираются из JSDoc исходника — из них подсказки в редакторе

Редактор, который знает колбэк

«Как там называлась переменная с адресом?» — больше не вопрос. Набираешь vars. и видишь параметры колбэка и переменные его рынков, вместе со значениями по каждому рынку.

  • TypeScript LanguageService в Web Worker: автодополнение, hover, сигнатуры, диагностика
  • Ни одного захардкоженного qa.* во фронтенде: декларации приходят с бэкенда
  • secrets. показывает только ключи — значение секрета в подсказку не попадает
  • ≈1 МБ TypeScript грузится только с первым открытым редактором
  • Run прогоняет скрипт с формы — без отправки и без Save

Инвариант двух баз

Мы читаем боевые тестовые базы рынков. Поэтому направление доступа зафиксировано жёстко — и защищено тестом, который обязан быть зелёным.

fillFromDb: trueрежим «Отправить по id»
POST /utilities/resolve-transactionзаполнение формы без отправки

Ровно два входа, больше ни одного. Обычная отправка колбэка в базу рынка не ходит вообще — это проверяет sendWithoutDbLookup.test.js. Переменные рынка — это строки нашей базы, а не чтение чужой.

Куда не попадает секрет

Переменная с secret: true видна только внутри скрипта, в объекте secrets. В {{...}} она не подставляется — значит, не может утечь ни в URL, ни в тело, ни в лог.

Подпись при этом всё равно получается: скрипт считает HMAC внутри песочницы и возвращает уже подписанное тело. Пустой на форме секрет можно держать переменной рынка — он всё равно уйдёт только в песочницу.

Бэкенд проверяется голым node:test и assert, подмена модулей — через require.cache. Ни sinon, ни proxyquire, ни node-mocks-http: меньше зависимостей — меньше того, что может сломаться не по нашей вине. Фронтенд — Vitest и отдельная проверка границ слоёв FSD.

Честно: чего мы не делаем

Презентация без этого слайда была бы рекламой. CAT — внутренний тестовый контур, и часть рисков принята осознанно, а не пропущена.

  • Наружу не смотрит. Доступа из интернета нет, данные — тестовые транзакции тестовых рынков.
  • Секреты колбэков лежат в базе открытым текстом. Записано в docs/RISK-ACCEPTANCE.md как принятый риск.
  • До Postgres нет TLS, JWT живёт в localStorage. Для внутреннего контура — приемлемо.
  • Условие отзыва: если инструмент выставят наружу или заведут в него настоящий ключ — все эти решения пересматриваются заново.

Главная мысль

Коллекция запросов описывает, как постучать в платёжную систему.

Нам нужно было описать, что такое колбэк — и дать это команде как сервис.

Поэтому платёжная система у нас — строка в базе,
подпись — скрипт в песочнице, общий код — пакет с версиями,
а история отправок — общая.
